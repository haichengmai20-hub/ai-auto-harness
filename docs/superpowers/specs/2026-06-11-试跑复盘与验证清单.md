## 二、发现的问题 (P1-P12)

### P0 级（最紧急）

#### P1: Cron 只跑一次就退出，不自动续跑

**现象**: fetch-weights 下载 47GB 权重需要跨 cron（超过单次 cron 的 wall-clock），但 daily.sh 跑完就退出，等到第二天 10:00 才重新跑。

**影响**: 24 小时延迟。如果下载在 10:30 完成，要等到第二天 10:00 才推进到 install-env。

**根因**: daily.sh 设计为单次执行，无续跑机制。

**方案**: daily.sh 退出后检查 workspace/*/state.json，如果有 in_progress 项目，30 分钟后重新启动 daily.sh（最多 3 次/天）。用 `nohup bash -c "sleep 1800 && bash cron/daily.sh" &` 替代 at 命令（本机无 at）。

**验证方法**:
1. 在某个 workspace 下创建 state.json: `{"slug":"test","phase":"fetch-weights","status":"paused_in_progress","phases_done":["intake"]}`
2. 运行 `bash cron/daily.sh`，等它退出
3. 检查 `state/resume-count-$(date +%Y-%m-%d).txt` 内容应为 1
4. 检查 `ps aux | grep "sleep 1800.*daily.sh"` 应有进程
5. 30 分钟后应自动启动新的 cron run

---

#### P4: GPU Preflight 不查实际空闲显存

**现象**: intake 阶段只检查 GPU 总量（8 卡 × 32GB = 256GB），不检查实际空闲显存。6 张卡被 3 个 Gemma vLLM 服务占了（每张 ~30GB），只有 2 张空闲，但 intake 给了 green light。

**影响**: 跑到 run-and-repair 阶段才发现 OOM，浪费 2 小时 + $80。

**根因**: preflight-gpu-disk SKILL.md 的判定规则只看单卡 used≥25GB 排除，没有做总空闲 VRAM 的聚合检查。

**方案**: 
1. 增加**空闲显存聚合检查**: `sum_free = Σ(可用卡的 free_MiB)`, 与模型总需求比较
2. 增加**API skeleton 降级路径**: 如果 GPU 不足但项目有 API 端点，走轻量 API 调用而非 self-host

**验证方法**:
1. 启动 3 个 vLLM 服务占 6 张 GPU
2. 运行 intake 对一个 14B 模型（需要 ~42GB VRAM）
3. 验证 intake.json 的 blocked 应包含 `gpu_vram_insufficient`
4. 验证 gpu_picks 应为空或只有实际空闲的卡

### P1 级

#### P3: State.json 与实际文件不一致

**现象**: 我们手动把 state.json 改为 fetch-weights done，但 fetch-weights.json 还是旧的 paused_in_progress。Agent 花 14 分钟反复确认已完成的工作。

**影响**: 14 分钟空转确认，token 浪费。

**根因**: 多处写 state（手动改、SubAgent 改、cron 改），无一致性校验。

**方案**: 新建 `scripts/reconcile-state.sh`，在 cron 启动前对账：
- 规则 1: fetch-weights paused 但文件已全在 → 修正为 done
- 规则 2: installing 但 venv 可用 → 修正为 done
- 规则 3: running 但后台 PID 已死 → 修正为 paused_in_progress

**验证方法**:
1. 创建一个 workspace，state.json 标记 fetch-weights/paused_in_progress
2. 实际把模型文件下载完（无 .incomplete 文件）
3. 运行 `bash scripts/reconcile-state.sh /root/ai-auto-harness`
4. 验证 state.json 应变为 fetch-weights/done

---

#### P6: Cron 失败后无自动重试

**现象**: claude-haha 异常退出（exit code ≠ 0）后 daily.sh 直接退出，不重试。

**影响**: 临时性错误（网络抖动、API 限流）导致整轮 cron 作废。

**方案**: daily.sh 的 cleanup trap 里加判断：如果 exit code ≠ 0 且不是续跑（`AI_HARNESS_IS_RESUME` 为空），15 分钟后重试。

**验证方法**:
1. 修改 claude-haha 路径为一个不存在的命令（模拟异常退出）
2. 运行 `bash cron/daily.sh`
3. 验证 cleanup.log 应有 "异常退出...15 分钟后重试"
4. 验证 15 分钟后应自动启动新的 cron run

### 规则级（P8-P12）

#### P8: 接续时 agent 看到 failed outcome 就跳过

**现象**: 我们重置 state.json 为 in_progress 并标注 `previous_failure=gpu_memory_insufficient_RESOLVED`，但 agent 看到之前的 record_outcome(failed) 记录后仍然跳过，去挑新项目。

**影响**: 资源条件变化（GPU 释放）后无法自动重试之前失败的项目。

**方案**: auto-daily SKILL.md 任务 1 加规则：如果 state.json 含 `previous_failure=*_RESOLVED`，必须重试而非跳过。`resume_reason` 字段提供重试上下文。

**验证方法**:
1. 在 state.json 中设置 `previous_failure: "gpu_memory_insufficient_RESOLVED"` + `resume_reason: "GPU 已释放"`
2. 运行 cron
3. 验证 agent 应选择接续该项目而非跳过

---

#### P9: install-env 不装未列出的依赖

**现象**: SCAIL 的 wan 分支代码 `import flash_attn`，但 requirements.txt 没列 flash-attn。install-env 只装 requirements.txt 里的包，run-and-repair 阶段才发现 AssertionError。

**影响**: 一个 `pip install flash-attn` 就能解决的问题，消耗了整个第 3 轮修复机会。

**方案**: install-env 第 6 步加 **import 深度预检**：
1. 扫描 repo 代码中 `import flash_attn` / `import xformers` 等常见推理依赖
2. 对每个引用的依赖做 `python -c "import <dep>"` 验证
3. 缺失则尝试 `pip install`
4. 安装失败不阻塞 install-env，但写入 `install.json.warnings`

**验证方法**:
1. 创建一个 repo，代码含 `import flash_attn`，requirements.txt 不含 flash-attn
2. 运行 install-env
3. 验证 install_env.log 应有 "[P9 precheck] 代码引用了 flash_attn，验证 import..."
4. 验证 flash_attn 应被安装（或 warnings 记录安装失败）

---

#### P10: run-and-repair 切 git branch

**现象**: agent 在 attempt 3 执行了 `git checkout wan`，丢掉了 attempt 1-2 的修复补丁（device placement fix），且 wan 分支代码结构与 main 完全不同。

**影响**: 之前的修复全部作废，且新分支可能引入新的未知问题。

**方案**: CLAUDE.md 新增 R4.2 规则：run-and-repair 严禁 `git checkout`/`git switch` 到其他分支。修复只能在当前分支上做。当前分支跑不通 → `paused_for_human`。

**验证方法**:
1. 在 run-and-repair SubAgent 的 prompt 中注入 R4.2 规则
2. 观察 agent 是否还会尝试 git checkout
3. 如果尝试，PostToolUse hook 应发出警告

---

#### P11: 3 轮修复上限太死

**现象**: SCAIL attempt 3 遇到 flash_attn 缺失（`AssertionError`），这只需 `pip install flash-attn`，但 3 轮上限已用完。

**影响**: 可修复的依赖缺失错误和不可修复的框架 bug 消耗相同的配额。

**方案**: CLAUDE.md R3 修复轮次分类：
- **依赖缺失类**（ModuleNotFoundError / AssertionError from import）→ 不计入 3 轮上限，可额外重试 2 次
- **框架 bug 类**（tensor mismatch / OOM / segfault）→ 正常计入 3 轮

**验证方法**:
1. 在 run-and-repair 中遇到 ModuleNotFoundError
2. 验证 agent 应继续修复而不因 3 轮上限放弃
3. 遇到 RuntimeError: tensor size mismatch
4. 验证应正常计入 3 轮上限

---

#### P12: R4 poll limit 截断长任务

**现象**: checkpoint resharding 需要 5-10 分钟，但 SubAgent 的 poll 上限 8 turn × 30s = 4 分钟就到了，被迫返回 paused_in_progress。

**影响**: 本可在一个 cron run 内完成的任务被拆成多次，每次都要重新初始化 agent 上下文。

**方案**: CLAUDE.md R4.1 poll 动态间隔：后台进程存活时 poll 间隔递增 30s→60s→120s（最多 3 次递增），减少空转 turn。PID 死或 sentinel 变 done/failed 立即恢复 30s。

**验证方法**:
1. 启动一个需要 5 分钟的后台进程
2. 观察 SubAgent 的 poll 行为
3. 验证 poll 间隔应从 30s 递增到 60s→120s
4. 总 turn 数应少于固定 30s 间隔的情况

## 四、SCAIL 失败根因总结

| Attempt | 分支 | GPU 配置 | 错误 | 分类 | 如果改善生效 |
|---------|------|---------|------|------|------------|
| 0 (归档) | main | 1-2 GPU | OOM (42GB > 32GB 单卡) | 资源不足 | P4 应在 intake 拦截 |
| 1 | main | 4 GPU MP=4 | device mismatch (T5/CLIP→cuda:0) | 代码 bug | 可修，正常消耗 1 轮 |
| 2 | main | 4 GPU MP=4 | tensor size 5120≠1280 | 框架 bug | 正常消耗 1 轮 |
| 3 | wan | 1 GPU | flash_attn AssertionError | 依赖缺失 | P9 应在 install-env 装装; P11 不计入上限 |

**如果所有改善生效**: SCAIL 应在 intake 阶段就被 P4 拦截（GPU 不足），走 api-skeleton 路径，省下 $105 和 4 小时。如果 GPU 充足，P9 会在 install-env 阶段装好 flash-attn，wan 分支应能跑通。
